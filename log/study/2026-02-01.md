## 복제 방식의 기본 개념

- 세 가지 복제 방식 비교: 단일 리더, 다중 리더, 리더 없는
- 다이나모(Dynamo) 관련
  - 아마존이 내부에서 사용한 후 데이터베이스용 아키텍처로 유행시킴
  - Cassandra, Riak이 다이나모 논문에서 영감을 받음
  - DynamoDB는 이름은 비슷하지만 내부 아키텍처가 다름 (DynamoDB는 단일 리더 기반)

## 리더 없는 복제 vs 다중 리더 복제의 핵심 차이

- 책임 소재의 차이
  - 다중 리더: 데이터 동기화, 충돌 해소를 DB 시스템에서 처리
  - 리더 없는: 클라이언트가 여러 노드를 읽어 최신 데이터를 판단하고 동기화 요청
- 동기화 방식
  - 리더 없는 구조에서는 클라이언트가 없으면 동기화가 이루어지지 않음
  - 읽기 시점에 동기화 처리(Read Repair) 또는 백그라운드 프로세스(Anti-Entropy)로 해결

## CDC(Change Data Capture) 개념 정리

- DB 외부 시스템에서 데이터 변경 사항을 캡처하기 위한 방식
- MySQL WAL 또는 MongoDB oplog도 CDC라 볼 수 있는가? -> 아님.
  - CDC vs 복제의 구분: CDC는 DB 외부 프로세스가 변경 감지 → 외부 시스템과 동기화 목적
    - 복제: DB 내부에서 일어나는 노드 간 동기화
    - 스트림을 받는 주체가 DB 내부냐 외부냐가 핵심 구분점
    - "CDC가 애초에 필요했던 이유가 DB 밖에 있는 시스템에서 데이터 변경 사항들을 받기 위한 거였으니까, 스트림을 받는 주체가 DB냐 아니냐가 중요하다."
  - WAL의 본래의 목적은 트랝개션 복구. 부가 용도가 복제 (oplog는 복제본 동기화가 본래 목적)
  - CDC는 이 로그들을 활용하는 방식

## 정족수(Quorum)와 느슨한 정족수

- 정족수 조건: W + R > N (쓰기 노드 + 읽기 노드 > 전체 노드)
  - r개의 복제 서버 중 최소 하나는 최근 성공한 쓰기를 알게 됨
- 느슨한 정족수(Sloppy Quorum)
  - 네트워크 장애 시 원래 타겟 노드가 아닌 다른 노드에 쓰기 허용 (정족수 불충족 상황에서도 쓰기 성공 처리)
  - 쓰기 키에 따라 타겟 노드가 보통 정해져있음 (키 해시 기반 노드 할당)
  - 장애 복구 후 홈 노드로 데이터 전송 (Hinted Handoff)
  - Cassandra에서는 기본 비활성화 상태

## Cassandra를 사용하는 이유

- Cassandra의 핵심 철학: "가용성을 최우선으로, 일관성은 유연하게. 완벽한 일관성보다는 항상 응답하는 시스템을 더 중요하게 생각한다."
- 쓰기 확장성의 차이
  - 리더 기반은 리더 수 만큼 쓰기 수용, 보통 리더의 수직 스케일업으로 대응
  - 리더 없는 구조는 모든 노드가 고루 쓰기 수용, 수평 스케일아웃으로 대응 가능
- 실제 사용 사례: 아마존 장바구니? -> 왜?
  - "장바구니에 담았는데 시스템 오류가 나면 매출 손실이다. 실패한 사용자 중 다시 담는 비율이 굉장히 적었고, 그걸 비용으로 계산해봤더니 높은 확률로 저장되도록 하는 게 매출 손실을 최소화하는 방향이라는 결론이 나왔을 것이다."

## fan-out 형태 요청 처리 아키텍처

- 문제 상황
  - SNS: 팔로워 1000만 명에게 게시글 전파 시 동시 쓰기 부하
- Cassandra 방식의 장점
  - 사용자별로 쓰기 노드가 해시 기반으로 분산
  - 1000만 명의 동시 쓰기도 전체 노드 스펙 합산으로 처리 가능
  - 리더 기반에서 노드 1000개 중 100개만 리더면 못 받지만, Cassandra는 1000개 모두 쓰기 가능
- 큐 기반 대안 아키텍처
  - 글 작성 → DB 저장 → 이벤트 트리거 → 팔로워 목록 조회 → 청크 단위(만 명씩) 큐잉 → 컨슈머가 순차 처리
  - 장점: 처리량 제어 가능, Fan-out 속도 일정
  - 단점: 지연 발생 (마지막 사용자는 막 10분, 100분 후 갱신될 수도)
  - 저지연이 필수가 아닌 경우 유효한 대안
- "지연을 허용한다면 큐 기반으로 청크 단위 순차 처리도 가능하다. 하지만 실시간에 가깝게 처리하려면 동시 쓰기 부하를 감당해야 하고, 그러려면 Cassandra 같은 구조가 유리하다."

## 마스터-슬레이브 읽기 분산 이슈

- 현재 운영 방식 (MySQL 기준)
  - 대부분 프라이머리에서만 읽기 수행 (정합성 우선)
  - 슬레이브/세컨더리는 Failover 용도로만 활용
  - 슬레이브 부하가 거의 없음 (복제 동기화 부하만 존재)
- MongoDB vs MySQL 차이
  - 라우팅: Mongos가 자동 처리 vs 별도 미들웨어 필요
  - 읽기 분산: secondaryPreferred 옵션 vs 애플리케이션에서 직접 지정
  - Failover: 자동 대응 vs 수동 대응 필요 가능
- MySQL도 Proxy 미들웨어로 mongos와 같은 역할 설정 가능하나 흔히 사용되는 방법인지는 의문
- 회사에서 MySQL 읽기 분산을 안 하는 정확한 이유 확인 필요

### 회사에서 Mysql의 replica를 읽기 전용으로 부하 분산을 안하는 이유

- Slave에 읽기 부하가 분산되어 있을 경우, Slave 장애 시 읽기 트래픽이 Master로 인입됨
- 이때, 부하의 총량이 DB 1대로 버틸 수 없는 양일 경우 연쇄 장애(Cascading Failure)가 발생할 수 있음
- 그렇다고 Slave 장애 상황에 페일오버를 안 하면 읽기 쿼리가 실패함
- 따라서, 부하의 총량을 DB 1대 기준으로 운영하여 장애 대응을 단순화함
  - Master 장애: MHA 자동 페일오버로 처리
  - Slave 장애: 서비스 영향 없음 (읽기 트래픽이 없으므로)
