## 모놀리식 아키텍처의 문제

> 모놀리식 아키텍처는 규모가 커짐에 따라 개발, 테스트, 배포, 확장이 어려워지는 지점이 옴

- 복잡도
  - 내용이 너무 방대해서 이해 및 수정에 시간이 많이 듬
  - 단일 코드베이스는 소통/조정 오버헤드를 유발
- 개발이 더딤
  - IDE 실행 속도 느려짐
  - 빌드 시간 증가
- 배포가 험난
  - 여러 개발자가 같은 코드베이스에 소스를 커밋하다 보니 릴리즈가 복잡
  - 브랜치 분리를 해도 머지 과정에서 고생
  - 이로 인한 테스트 및 코드 안정화 기간이 필요해짐
- 확장이 어려움
  - 모듈마다 리소스 요건이 맞지 않을 수 있음
  - 어떤 모듈은 고용량 메모리 요구, 어떤 모듈은 많은 CPU 코어 수를 요구 등...
  - 이를 모두 아우르는 서버 리소스 구성이 필요해져 복잡
- 장애 전파
  - 특정 모듈에 버그로 전체 애플리케이션 다운이 가능
- 기술 스택 최신화 어려움
  - 특성상 새로운 프레임워크, 언어 등을 받아들이기 어려움
  - 전체 재작성 또는 업데이트는 리스크

## 마이크로서비스 아키텍처 장점

- 지속적으로 전달/배포 가능
- 규모가 작아 관리 용이
- 독립적 배포/확장 가능
- 팀이 자율적
- 결합 격리가 잘됨
- 새로운 기술 도입 용이

## 마이크로서비스 아키텍처 단점

- 딱 맞는 서비스 찾기 어려움 (서비스 분리 기준을 잡기 어렵다는 뜻)
- 분산 시스템 복잡도로 인해 개발/테스트/배포가 어려움
- 여러 서비스에 걸친 기능 배포시 어려움
- 아키텍처 도입 시점 결정이 어려움

## 마이크로서비스 아키텍처 패턴 언어

- 패턴: 특정 상황에서 발생한 문제에 대한 재사용 가능한 해법
- 패턴은 맥락을 고려하게 만들고 자주 간과되는 솔루션의 측면도 함께 기술하도록 강제하여 효용성이 큼
- 상용 패턴의 구조
  - 강제 조항 (forces): 문제 해결을 위해 반드시 처리해야 할 이슈
    - 상충되는 조항이 있을 수 있음
    - 우선순위 선정이 중요
  - 결과 맥락 (resulting context): 패턴 적용 결과
    - 장점, 단점, 이슈(패턴 적용시 발생한 새로운 문제)로 구성
  - 연관 패턴 (related patterns): 다른 패턴들과의 관계를 기술
    - 선행자, 후행자, 대안, 일반화, 세분화로 5가지 관계가 있음
- 마이크로서비스 아키텍처 패턴 언어: 마이크로서비스를 중심으로 서로 관련된 소프트웨어와 디자인 패턴을 취합한 것
