# Virtual Thread

## 가상 스레드란?

- 일명 프로젝트 Loom
- JDK19에서 첫 preview, JDK21에서 final

### 해결하는 문제

가상 스레드와 리액티브 프로그래밍은 동일한 문제를 해결하고자 함

- 높은 처리량 달성 (High Throughput)
- I/O 블로킹으로 인한 자원 낭비 해결
- 플랫폼 스레드(Platform Thread)의 한계 극복
  - 운영체제 수준에서 동시에 실행 가능한 스레드 수는 수천 개(약 4000~5000개) 정도
  - 이로 인한 '요청당 하나의 스레드(One Thread Per Request)' 모델의 확장성 문제

-> 플랫폼 스레드가 블로킹되는 상황을 피하고 100% 가동되도록 유지하기 위한 방법

### 특징

- 플랫폼 스레드에 비해 1000배 가량 가벼움
- 기본적인 동작 원리: 플랫폼 스레드를 여러개의 가상 스레드들이 돌려씀
  - JDK 런타임이 스케줄링 처리
  - 가상 스레드의 스택및 정보는 힙에 저장
  - 블로킹 작업시 가상 스레드가 플랫폼 스레드에서 unmount되고, 다른 가상 스레드가 이를 할당받음
- 가상 스레드는 풀링을 하면 안됨
  - 매번 새로운 스레드 생성하여 사용 후 버려서 GC 되도록 유도
- 스레드를 블로킹하면 안됨 -> 가상 스레드는 블로킹해도 됨 (오히려 이 패턴이 맞음)
- 로직과 무관한 스택 트레이스 -> 호출 순서와 위치에 맞는 스택 트레이스
  - 가상 스레드 스택 트레이스에는 비동기 task(람다 함수) 등록 지점이 남아 디버깅에 용이
- loose thread -> autoclosable(structured concurrency) 덕분에 loose thread 방지
  - 가상 스레드는 풀링을 안하기 때문에 가능함 (플랫폼 스레드는 보통 풀링)

결과적으로 가상 스레드와 리액티브 프로그래밍의 결정적인 차이는 '**플랫폼 스레드를 블로킹하지 않도록 관리하는 책임이 누구한테 있는가?**'이다.

- 가상 스레드: JDK 런타임
- 리액티브 프로그래밍: 개발자

## structured concurrency 패턴

- scope.fork 형태로 실행하면 subtask 타입 반환 (future와 사실상 동일)
- try-catch 스코프 바깥으로 나가면 자원 모두 자동으로 정리됨 (스레드 포함. loose thread 방지)
- 하위 scope도 생성 가능 (트리 형태가 됨. 루트가 닫히면 하위 scope들도 닫힘)

## Scoped Values

- 스프링 부트 사용하면 스레드 로컬 사용하고 있는거임
- 스레드 로컬이 executorservice보다 먼저 생김
  - 스레드 로컬은 스레드를 생성하여 사용 후 죽으면서 함께 cleanup 되는 것을 의도했었음
  - 스래드 재사용을 하면 스레드 로컬을 직접 cleanup 해줘야 함 (remove)
- 스레드 로컬의 문제
  - mutable
  - VM이 최적화할 수 없음 (?)
  - 영원히 존재할 수 있음 (스레드 재사용으로 인해)
- 가상 스레드는 스레드 로컬 인터페이스를 지원하도록 구현됨. 하지만 대체제로 Scoped Values를 제시

## 가상 스레드 피닝(pinning) 이슈

- synchronized pinning
  - `synchronized` 블록 집입시 획득하는 monitor가 가상 스레드를 몰라 캐리어 스레드 id를 기록
  - 해당 블록 내에서 블로킹 작업 수행시 가상 스레드가 unmount되고 해당 플랫폼 스레드를 다른 가상 스레드가 점유
  - 이 케이스에서 새로운 가상 스레드가 동일한 `synchronized` 블록 진입을 시도하면 뚫림 (발생하면 안되는 케이스)
  - 따라서, 이러한 문제를 방지하기 위해 `synchronized` 진입시 플랫폼 스레드에 진입한 가상 스레드를 고정(pinning)함 -> 블록 종료 전까지 다른 가상 스레드는 해당 플랫폼 스레드 사용 불가능
  - JDK 24에서 모니터에 가상 스레드 id를 기록하는 지원을 추가하여 해당 문제를 해결함
- native pinning
  - 네이티브 코드에는 플랫폼 스레드 스택 메모리에 대한 주소 포인터가 존재할 수 있음
  - 따라서, 네이티브 코드는 동일한 플랫폼 스레드 위에서 돌아가야 함
  - 이를 위해 네이티브 코드를 호출하는 경우(스택에 네이티브 프레임이 있는 경우) 피닝이 발생함
  - JDK 24에서도 해결되지 않은 문제
- capturing file I/O

# JDK 25

- `JEP 506: Scoped Values` Final
- `JEP 505: Structured Concurrency` Fifth Preview
- `JEP 510: Key Derivation Function API` Final
  - KDF(Key Derivation Function): 솔트 추가 + 해시 수만번 적용하여 암호화 하는 방법 (e.g. PBKDF2, scrypt, bcrypt)
  - API 사용성 때문에 Bouncy Castle, Spring Security 등 외부 라이브러리 사용했었음
  - 사용성을 개선한 표준 API를 정식 기능으로 채택하여 외부 라이브러리 없이 처리 가능하도록 함
- `JEP 503: 32비트 x86 포트 제거` Final
  - JDK 25부터는 x86 32비트 OS에서 사용 불가능
- `JEP 519: Compact Object Headers` Final
  - 128비트(16바이트) -> 64비트(8바이트)로 객체 헤더 사이즈 감소
- `JEP 521: Generational Shenandoah` Final
