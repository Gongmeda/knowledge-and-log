# 복제

## 복제가 필요한 이유

- 지연 시간 감소 (지리적 거리 감소로 인한)
- 가용성 증가
- 처리량 증가

> 복제의 모든 어려움은 '변경' 처리에 있음

## 단일 리더 복제

> 쓰기는 리더만 허용. 읽기는 리더 또는 팔로워에게 질의

### 동기 vs 비동기 복제

- 동기식
  - 팔로워가 쓰기를 수신했는지 확인해줄 때까지 대기
  - 팔로워가 리더와 일관성 있게 최신 데이터 복사본을 가짐
  - 팔로워가 응답하지 않으면 쓰기 처리 장애
- 비동기식
  - 메시지를 전송하지만 팔로워의 응답을 기다리지 않음

- 모든 팔로워가 동기인 상황은 비현실적 (팔로워 하나는 동기, 나머지는 비동기. 반동기식이라 부름)
- 보통은 완전히 비동기식으로 구성
  - 많은 팔로워, 지리적 분산 상황에서 많이 사용

새로운 팔로워 설정

- DB를 잠가서 일관성 보장하는건 가용성 저하하여 안됨
- 보통 중단없이 수행 가능
  1. 스냅샷을 일정 시점에 가져옴 (락 없이 처리)
  2. 스냅샷을 팔로워에 반영
  3. 팔로워가 리더에게 스냅샷 이후 데이터를 요청 (스냅샷 로그의 정확한 위치 기반)
  4. 팔로워가 리더를 따라잡으면 그때부터 이어서 데이터 변화 처리 수행

### 노드 중단 처리

> 라더 기반 복제에서의 고가용성 달성 방법

팔로워 장애: 따라잡기 복구

- 디스크에 저장된 마지막 트랜잭션 기반으로 리더를 따라잡아 복구

리더 장애: 장애 복구

- 팔로워 리더로 승격, 새로운 리더로 쓰기 전송, 팔로워들이 바라보는 리더 변경 등 작업이 필요
- 예시 자동 장애 복구 시나리오
  1. 리더 장애 판단: 보통 타임아웃으로 처리. 일정시간 응답 없을 경우 죽은걸로 간주.
  2. 새로운 리더 선택: 선출 과정 또는 제어 노드에 의해 정해짐. 보통 가장 최신 변경사항을 가진 팔로워.
  3. 시스템 재설정: 이전 리더가 팔로워가 되고 새로운 리더를 인식하게끔 처리
- 장애 여지 포인트
  - 이전 리더가 다시 팔로워로 참여했을 때 미반영분은 어떻게 처리하는가?
    - 가장 단순한 방법은 폐기
  - DB 외부 시스템이 DB 내용에 맞춰져야 하는 케이스에는 위험
    - e.g. redis 키로 DB의 auto increment 키를 사용하면 페일오버 과정에서 승격된 노드의 increment 키가 redis의 데이터와 충돌할 수 있음
  - 스플릿 브레인: 두 노드가 리더로 승격되는 상황. 데이터 유실/오염 위험이 있고, 감지 메커니즘으로 해소할 수 있지만 최악의 경우 두 노드 모두 종료될 수도 있음
  - 리더 장애 판단 기준(타임아웃)이 애매 (너무 길거나 짧으면 안됨)

### 복제 로그 구현

> 실제 복제 동작 방식

구문 기반 복제

- 모든 쓰기 쿼리문을 전송하는 방식
- 비결정적 함수, 현 데이터에 의존적인 쿼리 등 부수효과가 있는 구문으로 인해 복제가 깨질 여지가 있음
- 구문을 안전하게 변환해서 해소 가능

쓰기 전 로그 배송

- 모든 쓰기는 로그에 기록 (append-only 바이트 열)
- 바이트 단위의 상세 정보를 명시하기 때문에 복제가 저장소 엔진과 엮임

논리적(로우 기반) 로그 복제

- 저장소 엔진에 대한 의존성을 없애기 위해 복제를 위한 별도 형식을 사용
- RDB는 대개 로우 단위로 기술
- 하위 호완성 유지가 더 쉽고, 리더/팔로워간에 서로 다른 DB 버전, 다른 DB 소프트웨어 사용이 가능
- 외부 애플리케이션이 사용하기도 쉬워 CDC(change data capture)에 활용

트리거 기반 복제

- 애플리케이션 코드를 등록하고, 데이터가 변경되면 자동으로 실행 (트리거)
- 다른 복제에 비해 오버헤드가 있으나, 유연성이 필요한 경우 유용

### 복제 지연 문제

> 읽기 처리량 증가를 위해 읽기 확장시 복제 지연에 따른 상태 불일치 등의 문제가 발생 (최종적 일관성)

쓰기 후 일관성

- 자신이 쓴 내용을 다시 읽을 때 반영이 안되어 보이는 현상을 방지하기 위함
- 가능한 구현 방법
  - 사용자가 수정한 내용은 리더에서 읽기
  - 마지막 갱신 시각 기준으로 1분 동안은 리더에서 읽기
  - 클라이언트가 기억하는 가장 최근 쓰기의 타임스탬프를 사용하기
  - 복제 서버가 여러 데이터센터에 분산된 경우, 리더가 포함된 데이터센터로 라우팅
- 디바이스 간
  - 마지막 갱신 타임스탬프를 클라에서 기억하면 안됨 (중앙집중식으로 관리 필요)
  - 리더에서 읽어야 하면 동일한 데이터센터로 라우팅 필요

단조 읽기(monotonic read)

- 한 사용자가 여러번 읽어도 시간이 되돌아가는 현상을 보지 않는다는 의미
- 각 사용자가 동일한 복제 서버에서 수행되데끔 보장하여 구현

일관된 순서로 읽기(consistent prefix read)

- 일련의 쓰기가 특정 순서로 발생했을 때, 이를 읽는 모든 사용자가 같은 순서로 읽는걸 보장하는 것
- 파티셔닝된 DB에서 발생하는 문제
- 인과성이 있는 쓰기가 동일한 파티션에 기록되게끔 해서 구현

### 복제 지연을 위한 해결책

- 애플리케이션이 DB보다 강력한 보장을 구현
- 트랜잭션
  - 애플리케이션이 단순해지기 위해 DB에서 강력한 보장을 제공
  - 많은 분산 시스템에서는 트랜잭션을 포기 (가용성, 성능 측면에서 비쌈)
