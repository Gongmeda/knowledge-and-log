## 애플리케이션 레벨 샤딩 실사례

- Redis 클러스터가 회사에서 지원되지 않던 시절, 용량 한계로 여러 대의 단독 Redis를 띄우고 애플리케이션 코드에서 유저 ID 해시 기반으로 직접 라우팅하는 방식을 사용
- DB에서 지원하면 애플리케이션은 데이터가 물리적으로 어디 저장되는지 몰라도 되고, 리밸런싱도 DB가 알아서 해줌
- 애플리케이션 레벨에서 하면 샤딩 키 변경, 핫스팟 대응, 리밸런싱을 개발자가 직접 해야 함


## Redis Cluster
- 16,384개의 고정 슬롯 기반 자동 샤딩을 지원
- 노드 추가/제거 시 슬롯 단위로 데이터를 이동시켜 리밸런싱
- 조회시 CRC16(key) % 16384로 해당 키가 속하는 슬롯 번호를 계산 -> 해당 슬롯이 있는 노드에 요청
- 요청을 받은 노드가 해당 슬롯을 소유하고 있으면 직접 응답한다. 소유하지 않으면 실제 소유 노드의 주소를 담아 `MOVED` 응답을 반환
- 실제로 Lettuce, Jedis 같은 Redis 클라이언트 라이브러리들은 연결 시점에 `CLUSTER SLOTS` 또는 `CLUSTER SHARDS` 명령으로 전체 슬롯-노드 매핑을 받아옴
- 코디네이터 없이 클라이언트가 직접 올바른 노드를 찾아가는 구조

## Cassandra 코디네이터와 Speculative Execution

- 클라이언트가 특정 노드(코디네이터)에 요청을 보내면, 코디네이터가 여러 노드로 분산 후 결과를 조합하여 응답
- 코디네이터가 죽으면 클라이언트 드라이버가 초기 연결 시 받은 클러스터 토폴로지 정보를 기반으로 다른 노드로 재시도
- Speculative Execution 옵션
  - 응답을 기다리다가 임계 시간(~10ms)이 지나면 실패를 기다리지 않고 다른 노드에 비동기로 동일 요청을 보내어, 먼저 응답이 오는 것을 사용하는 방식
  - 부작용으로 중복 쓰기와 전체 요청 수 증가가 있으며, 정합성 관리는 애플리케이션 책임
  - 기본값은 꺼져 있음

## MySQL vs MongoDB 쓰기 성능 차이의 원인

- MySQL
  - 스키마 밸리데이션(컬럼 타입 검증 등)이 엄격
  - B-tree 인덱스의 in-place 업데이트로 트리 구조 변경 오버헤드가 쓰기 시점에 발생
- MongoDB
  - WiredTiger 엔진이 LSM-tree 기반이라 일단 빠르게 쓰고 백그라운드에서 컴팩션으로 정리하는 방식이므로, 쓰기 시점의 연산이 상대적으로 단순
  - 스키마리스 특성상 밸리데이션 오버헤드도 적음
